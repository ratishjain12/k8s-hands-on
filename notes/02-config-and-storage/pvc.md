# PersistentVolume and PersistentVolumeClaim

Exercise 5. Manifests: [labs/02-config-and-storage/pvc/](../../labs/02-config-and-storage/pvc/)

A **PVC** is a namespaced request for storage. A **PV** is the actual storage, and it's cluster-wide. A Pod mounts the PVC, never the PV. The storage then outlives the Pod, which `emptyDir` can't do ([emptydir.md](emptydir.md)).

## The claim

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: lab-pvc
spec:
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 100Mi
```

No `storageClassName`, so the claim uses the default class, `standard` ([storageclass.md](storageclass.md)). `storageClassName: ""` would use no class and skip dynamic provisioning.

### accessModes

| Mode | Meaning |
|---|---|
| `ReadWriteOnce` (RWO) | Read-write, mounted by a single **node**. Several Pods on that node can share it. |
| `ReadOnlyMany` (ROX) | Read-only, by many nodes |
| `ReadWriteMany` (RWX) | Read-write, by many nodes |
| `ReadWriteOncePod` (RWOP) | Read-write, by a single **Pod** in the cluster |

What's available depends on the backend. `standard` (local-path) supports RWO only. A claim asking for something the backend can't do stays `Pending`. This is from the docs. Only RWO was used here.

## Mounting it in a Pod

```yaml
volumeMounts:
  - name: pvc-volume
    mountPath: /usr/shared
volumes:
  - name: pvc-volume
    persistentVolumeClaim:
      claimName: lab-pvc
```

Note the field name: `persistentVolumeClaim.claimName`, compared with `configMap.name` and `secret.secretName`.

## Observed: dynamic provisioning

`kubectl get pv,pvc -A` after applying the claim and the Pod:

```
persistentvolume/pvc-47b8...   100Mi   RWO   Delete   Bound   default/lab-pvc   standard
persistentvolumeclaim/lab-pvc  Bound   pvc-47b8...  100Mi  RWO  standard
```

`kubectl describe pvc lab-pvc` events:

```
WaitForPodScheduled    waiting for pod pvc-pod to be scheduled
ExternalProvisioning   Waiting for a volume to be created by the external provisioner 'rancher.io/local-path'
Provisioning           External provisioner is provisioning volume for claim "default/lab-pvc"
ProvisioningSucceeded  Successfully provisioned volume pvc-47b8...
```

1. The PVC and a Pod using it were created.
2. Because of `WaitForFirstConsumer`, nothing happened until the scheduler placed the Pod (`WaitForPodScheduled`).
3. The `local-path-provisioner` made a directory on that node and created the PV, in about 4 seconds.
4. The PV was bound to the PVC.

| Column | Meaning |
|---|---|
| `STATUS: Bound` | PV and PVC are matched one-to-one |
| `VOLUME` on the PVC, `CLAIM` on the PV | The link in each direction |
| `RECLAIM POLICY: Delete` | Copied from the StorageClass at creation |
| PV name `pvc-<uid of the claim>` | Generated by the provisioner |

`describe pvc` also shows `Used By: pvc-pod`.

The PV has no namespace, so it shows without one in `get pv,pvc -A`. On local-path the `100Mi` is just a number in the objects, and the directory is not capped. This is from the docs and was not tested here.

## Reclaim policy

It decides what happens to the PV and data when the PVC is deleted.

```yaml
# StorageClass: a top-level field, there is no spec
reclaimPolicy: Retain

# PV: copied from the class when the PV is created
spec:
  persistentVolumeReclaimPolicy: Retain
```

- `Delete`: the PV and its data are removed with the PVC.
- `Retain`: the PV and data are kept for a manual cleanup.
- Changing the class later doesn't change existing PVs. A single PV can be changed with `kubectl patch pv <name> -p '{"spec":{"persistentVolumeReclaimPolicy":"Retain"}}'`.

## Data survives the Pod, not the PVC

Both tests were run on a throwaway PVC and Pod (`tmp-pvc`, `tmp-pvc-pod`, mounted at `/data`), not on `lab-pvc`. They were deleted afterwards.

**Pod delete.** Wrote a marker with `echo MARKER > /data/marker.txt`, deleted the Pod, applied the manifest again, and listed the directory:

```
marker.txt
MARKER
```

The PVC stayed `Bound` throughout, and the new Pod mounted the same PV. This is the opposite of `emptyDir` ([emptydir.md](emptydir.md)). A marker was needed because a Pod command that appends to a file writes on every start. That would look the same as surviving data.

**PVC delete** (with `reclaimPolicy: Delete`). Deleted the Pod, then `kubectl delete pvc tmp-pvc`. The PV `pvc-5a7e...` was gone from `kubectl get pv` within a few seconds, and only `lab-pvc`'s PV remained. The data went with it. The Pod was deleted first. What happens when a PVC is deleted while a running Pod still uses it was not tested.

| Delete | Data |
|---|---|
| Pod | Kept (PVC and PV remain) |
| PVC, with `Delete` | Gone (the PV is removed too) |
| PVC, with `Retain` | Not tested. Expected: the PV is kept, in a `Released` state, for manual cleanup. |

## Production StorageClasses

From provider docs, not run here. On AWS, EBS (`gp3`, `io2`) is block storage and RWO. EFS and FSx are shared filesystems and RWX. Production classes often use `Retain`, `WaitForFirstConsumer` (an EBS volume lives in one availability zone), and `allowVolumeExpansion: true`.
